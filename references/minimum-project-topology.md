# 项目最小拓扑

## 定义

项目最小拓扑是在工具、模型、人员、窗口和实现方式变化后，仍能保持项目身份与核心能力的最小关系结构。

这里的“最小”优先采用 `minimal` 而非 `minimum`：不要求证明它是所有可行结构中节点数量绝对最少，只要求当前结构中的每个核心节点和关系都不可无理由删除。

## 删除测试

对候选核心元素逐项提问：

1. 删除它后，项目是否仍服务同一对象？
2. 是否仍产生同一种关键价值变化？
3. 是否仍能判断成功与失败？
4. 是否仍能守住安全、法律、数据和权限边界？
5. 是否仍能跨环境恢复并继续演化？

全部不受影响时，该元素通常不属于项目身份核心。

## 六类核心关系

### Goal → Boundary

边界必须保护具体目标。无法说明保护什么目标的边界，可能是历史包袱。

### Goal → Contract

契约必须承载从当前状态到目标状态的必要转换。不能指向目标的接口是疑似旁路。

### Contract → Implementation

实现通过契约接入，不能反向绑架目标。替换实现时，契约与验收应保持稳定。

### Result → Evidence

结果必须留下可核查证据。没有证据的能力不能作为稳定基础继续叠加。

### Evidence → Goal

验收证据必须直接证明目标状态，而不是只证明流程运行过。

### Evidence → Evolution

演化只能由真实证据驱动，并受目标与边界约束。

## 核心分类

- `Invariant`：跨实现必须保持。
- `Essential Support`：当前必要，但理论上可替换。
- `Implementation`：默认可替换。
- `Experiment`：尚未验证，不得进入硬约束。
- `Burden`：不服务目标、证据或边界，建议删除。

## 最小拓扑成立条件

- 目标能被一句话说明；
- 边界能指出其保护对象；
- 核心契约有明确输入、转换、输出和错误语义；
- 验收证据直接对应目标；
- 实现可替换而不改变项目身份；
- 演化规则包含验证和回退；
- 新维护者可以从外部状态恢复当前项目。
